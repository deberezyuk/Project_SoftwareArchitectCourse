# Реакция системы на изменение: добавление новых метрик телеметрии

**Вероятность изменения:** 25%  
**Домен инициации:** Telemetry (обновление ПО на датчиках)  
**Связанные домены:** Telemetry, DrivingAnalytics, Recommendations, Notifications, Platform (API Gateway, BFF), Mobile

## 1. Анализ изменения

- Новые поля в сырых данных телеметрии → увеличение объёма информации.
- Появляются новые метрики стиля вождения (например, плавность поворотов, частота перестроений, время реакции).
- Меняется бизнес-логика расчёта коэффициента стиля вождения (добавляются новые веса и параметры).

## 2. Пошаговый процесс реализации изменений

### 2.1 Telemetry Domain

| Сервис / Компонент | Действие |
|--------------------|----------|
| **GatherTelemetry Service** | — Обновить схему десериализации сообщений из Kafka IoT (добавить новые поля).<br>— Расширить таблицу `RawTelemetryPoint` в TelemetryDB (новые колонки, возможно, JSONB для гибкости). |
| **FormTripsTelemetry Service** | — Изменить логику детектирования поездок, если новые данные влияют на начало/конец поездки.<br>— Дополнить расчёт базовых метрик (например, среднее боковое ускорение).<br>— Обновить формат события `trip_formed` (Kafka) и файлы в MinIO. |

### 2.2 DrivingAnalytics Domain

| Сервис / Компонент | Действие |
|--------------------|----------|
| **FormTripWithMetrics Service** | — Адаптировать обработку обновлённого события `trip_formed`.<br>— Реализовать расчёт новых сложных метрик. |
| **DrivingProfile Service** | — Добавить новые поля в API (GET/PUT) для хранения и отображения метрик. |
| **CalculateDrivingCoefficient Service** | — Пересмотреть весовые коэффициенты в формуле.<br>— Изменить ночной расчёт (загрузка дополнительных данных, пересчёт истории). |
| **База данных DrivingAnalytics** | — Добавить колонки для новых метрик в таблицы поездок, метрик, профиля. |

### 2.3 PolicyManagement Domain

Изменения не требуются, если новые метрики не влияют на базовые атрибуты полиса (например, срок действия, статус).

### 2.4 Recommendations & Notifications

| Сервис | Действие |
|--------|----------|
| **RecommendationService** | Обновить логику формирования рекомендаций (учитывать новые метрики, если они влияют на советы). |
| **NotificationService** | Добавить новые типы уведомлений (например, «улучшилась плавность вождения»). |

### 2.5 Platform (API Gateway, BFF)

| Компонент | Действие |
|-----------|----------|
| **External API Gateway** | Обновить схемы API (добавить поля в ответы) при необходимости версионирования. |
| **Internal API Gateway** | При необходимости добавить маршруты для новых endpoints. |
| **BFF Service** | Адаптировать агрегацию данных для мобильного приложения. |

### 2.6 Mobile приложение

| Компонент | Действие |
|-----------|----------|
| **Mobile Backend** | Доработать логику получения и передачи новых метрик. |
| **Mobile Frontend** | Отображать новые метрики в UI (экран поездок, профиль вождения). |

## 3. Риски и их митигация

| Риск | Митигация |
|------|------------|
| **Несовместимость версий датчиков** – старые датчики не шлют новые поля. | Использовать значения по умолчанию (`NULL`, 0) в БД и коде. Обратная совместимость десериализации. |
| **Снижение производительности** – рост объёма данных. | Провести нагрузочное тестирование. Оптимизировать индексы, добавить партиционирование. |
| **Рассинхронизация при развёртывании** – сначала обновление БД, потом кода, или наоборот. | Использовать миграции с блокировками и стратегию «сначала добавить колонки, потом код». |
| **Скачок стоимости полиса** – новые веса в коэффициенте. | Протестировать на исторических данных, развернуть A/B-тестирование. |
| **Поломка старых версий мобильного приложения** – новые поля в API. | Внедрить версионирование API (например, `/v2/metrics`). Старые версии продолжают получать прежние ответы. |
| **Потеря событий в Kafka** – изменение формата. | Увеличить retention, использовать совместимые схемы (Avro с эволюцией, добавление полей как optional). |

## 4. Рекомендации по безопасному внедрению

1. **Feature toggles** – новые метрики включаются флагом в конфигурации.
2. **Миграция данных поэтапно**:
   - Добавить колонки в БД со значением по умолчанию.
   - Обновить сервисы-потребители (FormTripWithMetrics, CalculateDrivingCoefficient).
   - Обновить сервисы-производители (FormTripsTelemetry).
3. **Тестирование**:
   - Модульное – новых расчётов метрик.
   - Интеграционное – взаимодействия через Kafka и MinIO.
   - Нагрузочное – с эмуляцией потока новых данных.
4. **Мониторинг**:
   - Следить за размером сообщений в Kafka, задержками обработки.
   - Добавить метрики в Prometheus для новых метрик (частота, распределение значений).
5. **Документирование** – обновить ADR, спецификации API, схемы БД.

## 5. Заключение

Изменение является локальным для доменов Telemetry и DrivingAnalytics, с небольшим влиянием на Recommendations, Notifications и мобильное приложение. При соблюдении рекомендаций по обратной совместимости и версионированию риски управляемы, а модифицируемость системы оценивается как высокая (требуется изменить ~4 сервиса из 15, CPI ≈ 0.27).
