## Недоступность master‑БД Telemetry

### Контекст
- **Что произошло:** Master‑экземпляр БД Telemetry (PostgreSQL + TimescaleDB) стал недоступен (сбой узла, сетевые проблемы, перегрузка).
- **Влияние на процесс:** Запись новых точек телеметрии останавливается. Чтение из read replica продолжает работать. Пользователи не видят новые поездки и актуальные метрики. Данные в Kafka накапливаются.

### Основные механизмы отказоустойчивости
- **Failover БД с продвижением read replica** – при отказе master реплика автоматически (или вручную) становится новым master.
- **Retry‑механизм на уровне сервиса** – GatherTelemetry повторяет попытки записи.
- **Увеличенный retention в Kafka** – данные телеметрии накапливаются на время простоя.

### Реакция системы (по шагам)
1. **GatherTelemetry Service**  
   - При попытке записи в master получает ошибку.  
   - Не коммитит смещение (offset) сообщений в Kafka.  
   - Выполняет retry (5 попыток с задержкой 1,2,4,8,16 сек).  
   - После исчерпания попыток логирует ошибку и продолжает чтение (сообщения не удаляются).

2. **Kafka (телеметрия)**  
   - Сообщения накапливаются в топиках (retention увеличен до 7 дней).

3. **Механизм failover БД**  
   - Используется Patroni (или managed Multi-AZ) для автоматического продвижения read replica до master.  
   - RTO ≤ 10 минут, RPO ≤ 1 минута (потеря не среплицированных данных).  
   - После переключения обновляется DNS / Service для GatherTelemetry.

4. **FormTripsTelemetry Service**  
   - Продолжает читать из read replica (она доступна). Новые поездки не формируются.

5. **BFF и мобильное приложение**  
   - Отображают кэшированные данные (из Redis).  
   - Показывают плашку: «Данные о поездках обновляются с задержкой».

6. **Восстановление**  
   - После promote реплики GatherTelemetry успешно записывает накопленные сообщения (retry завершается).  
   - FormTripsTelemetry обрабатывает данные, публикует события.  
   - Плашка в приложении исчезает.

### Необходимые компоненты для реализации
- **Read replica БД Telemetry** (PostgreSQL, настроенная асинхронная репликация).
- **Patroni (или managed Multi‑AZ)** для автоматического failover.
- **Увеличенный retention в Kafka** (7 дней).
- **Retry‑механизм с экспоненциальной задержкой** в GatherTelemetry.
- **Redis (кэш в BFF)** для отображения последних данных пользователю.
- **Плашка / уведомление в мобильном приложении**.
- **Мониторинг (Prometheus + алерты)** для контроля доступности master и лага репликации.
