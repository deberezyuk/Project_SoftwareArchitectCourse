# Реакция системы на изменение: добавление нового страхового продукта

**Вероятность изменения:** 25%  
**Домен инициации:** PolicyManagement (продуктовое требование)  
**Связанные домены:** PolicyManagement, DrivingAnalytics, Notifications, Platform (API Gateway, BFF), Mobile  
**Не затрагиваются:** Telemetry, Pricing (логика во внешней системе), Recommendations (инкапсулирована в LLM)

## 1. Анализ изменения

- Появляется новый тип полиса (например, «CASCO Light», «Электро-КАСКО», «Семейный полис»).
- Новый продукт может иметь:
  - Другую базовую стоимость (хранится в PolicyManagement).
  - Иной набор учитываемых метрик вождения.
  - Отличные веса в расчёте коэффициента (но сам расчёт выполняется внешней системой тарификации).
  - Свои условия (например, минимальный стаж вождения).
- Telemetry не меняется – сбор данных одинаков для всех продуктов.
- Pricing не меняется – внешняя система тарификации получает коэффициент и базовые параметры, логика ценообразования там.
- Recommendations не меняется – LLM-платформа генерирует текст на основе переданных метрик, не привязанных к продукту.

## 2. Пошаговый процесс реализации изменений

### 2.1 PolicyManagement Domain

| Сервис / Компонент | Действие |
|--------------------|----------|
| **База данных** | — Добавить запись о новом продукте в справочник `InsuranceProduct` (поля: `productId`, `name`, `basePremium`, `applicableVehicleTypes`).<br>— При необходимости добавить новые атрибуты в таблицу `InsurancePolicy` (например, `productSpecificData` в JSON). |
| **PolicyManagement Service** | — Реализовать API для создания полиса с новым продуктом.<br>— Добавить валидацию соответствия автомобиля продукту.<br>— Обновить логику отмены динамического ценообразования, если для продукта это разрешено. |
| **Insurer Service** | — Если продукт влияет на правила андеррайтинга, добавить проверки. |
| **Vehicle Service** | — Возможно, добавить новые атрибуты автомобиля (тип кузова, год выпуска), релевантные для продукта. |

### 2.2 DrivingAnalytics Domain

| Сервис / Компонент | Действие |
|--------------------|----------|
| **База данных** | — Добавить поле `productId` в таблицы поездок и профилей (или связать через `policyId`). |
| **FormTripWithMetrics Service** | — При сохранении метрик привязывать их к продукту (через `policyId`). |
| **DrivingProfile Service** | — Расширить API, чтобы возвращать метрики и коэффициент в разрезе продукта (если у клиента несколько полисов разных типов). |
| **CalculateDrivingCoefficient Service** | — Модифицировать ночной расчёт: учитывать правила продукта (веса, пороги). Возможно, запускать отдельные экземпляры расчёта для разных продуктов. |

### 2.3 Notifications Domain

| Сервис | Действие |
|--------|----------|
| **NotificationService** | — Добавить шаблоны уведомлений для нового продукта (приветственные, изменения цены, рекомендации). |

### 2.4 Platform (API Gateway, BFF)

| Компонент | Действие |
|-----------|----------|
| **External API Gateway** | — Добавить новые endpoints для получения списка продуктов, для создания полиса с новым продуктом. Обновить схемы ответов. |
| **Internal API Gateway** | — При необходимости добавить маршруты для новых внутренних вызовов. |
| **BFF Service** | — Адаптировать агрегацию: передавать информацию о продукте в мобильное приложение. |

### 2.5 Mobile приложение

| Компонент | Действие |
|-----------|----------|
| **Mobile Backend** | — Доработать API вызовы для работы с новым продуктом. |
| **Mobile Frontend** | — Добавить экран выбора продукта при оформлении, отображение специфических метрик и условий. |

## 3. Риски и их митигация

| Риск | Митигация |
|------|------------|
| **Неоднозначность требований** – разные веса, пороги могут быть неправильно интерпретированы. | Тесное взаимодействие с бизнес-аналитиками; написание acceptance-тестов. |
| **Сложность расчёта коэффициента** – разные формулы для разных продуктов могут привести к дублированию кода. | Вынести расчёт в отдельный модуль (стратегия), конфигурируемый правилами. |
| **Производительность** – увеличение числа расчётов из-за новых продуктов. | Оптимизировать запросы, использовать кэширование тарифных правил. |
| **Совместимость с существующими клиентами** – старые полисы не должны затронуться. | Внедрить версионирование API; новые продукты добавляются без изменения старых. |
| **Ошибки в миграции БД** – некорректное добавление полей. | Использовать миграции с проверкой (например, Flyway). |
| **Несинхронизированное обновление сервисов** – сначала обновили API, а логика расчёта ещё старая. | Применять feature toggles; обновлять в порядке: сначала БД, затем сервисы-потребители. |
| **Внешняя система тарификации не знает о новом продукте** – нужно синхронизировать справочники. | Связаться с владельцами внешней системы, добавить продукт в их справочник. |

## 4. Рекомендации по безопасному внедрению

1. **Расширяемая конфигурация** – все параметры нового продукта (базовая цена, веса метрик, пороги) хранить в БД или конфиг-файлах, а не в коде.
2. **Feature toggle** – новый продукт можно включить для ограниченной группы клиентов (A/B-тестирование).
3. **Версионирование API** – `/v1/products`, `/v2/products` для обратной совместимости.
4. **Мониторинг** – добавить метрики по количеству созданных полисов нового типа, частоте расчётов, ошибкам.
5. **Тестирование**:
   - Модульное: проверка привязки метрик к продукту.
   - Интеграционное: создание полиса, получение прогноза цены.
   - Нагрузочное: массовое оформление полисов нового типа.
6. **Синхронизация с внешней системой тарификации** – обновить справочник продуктов в ней до внедрения изменений.

## 5. Заключение

Изменение локализовано в PolicyManagement, DrivingAnalytics, Notifications, API Gateway, BFF и Mobile. Telemetry, Pricing (внешняя система) и Recommendations (LLM) не требуют модификации. Модифицируемость оценивается как высокая (CPI ≈ 0.2–0.25). При использовании конфигурации правил и feature toggles риски минимальны.
