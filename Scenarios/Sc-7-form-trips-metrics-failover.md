## Недоступность FormTripWithMetrics Service (DrivingAnalytics)

### Контекст
- **Что произошло:** Сервис `FormTripWithMetrics` (домен DrivingAnalytics) стал недоступен (сбой кода, исчерпание ресурсов, отказ подов в Kubernetes).
- **Влияние на процесс:**  
  - Новые поездки не сохраняются в БД DrivingAnalytics.  
  - Сложные метрики не рассчитываются.  
  - Событие `trip_metrics_calculated` не публикуется.  
  - Ночной расчёт коэффициента (`CalculateDrivingCoefficient`) не получает свежие метрики → коэффициент не обновляется.  
  - Прогноз стоимости полиса и его обновление в системе страхового учёта останавливаются.  
  - Пользователь не видит новые поездки и актуальные метрики в профиле вождения.

### Основные механизмы отказоустойчивости
- **Накопление событий в Kafka** – сообщения `trip_formed` остаются в топике (retention 7 дней).
- **Retry-механизм** на стороне консьюмера (`FormTripWithMetrics`) – при запуске обрабатывает накопленные сообщения.
- **Кэширование (Redis) и read replica** – для отображения пользователю последних корректных данных (коэффициент из кэша, старые поездки из read replica).
- **Плашка в мобильном приложении** – информирование о временной задержке обновления.
- **Мониторинг** – отслеживание лага консьюмера (consumer lag) в Kafka.

### Реакция системы (по шагам)
1. **Kafka (корпоративная)**  
   - Сообщения `trip_formed` накапливаются в топике (retention 7 дней).  
   - Consumer lag (отставание) растёт.

2. **FormTripWithMetrics Service** (недоступен)  
   - Поды не обрабатывают сообщения.  
   - Kubernetes пытается перезапустить поды (readiness/liveness probes).  
   - При неудаче – поды остаются в состоянии CrashLoopBackOff.

3. **BFF и мобильное приложение**  
   - BFF читает данные о поездках из **read replica** DrivingProfileDB (старые поездки, метрики).  
   - Коэффициент стиля вождения и прогноз стоимости берутся из **кэша Redis** (последние успешно рассчитанные значения).  
   - Пользователь видит данные на момент до сбоя (коэффициент не меняется).  
   - Отображается плашка: «Данные о поездках временно не обновляются, скоро всё восстановится».

4. **CalculateDrivingCoefficient Service** (ночной)  
   - При отсутствии новых метрик за сутки расчёт коэффициента не выполняется (или использует старые данные).  
   - Событие `driving_coefficient_updated` не публикуется.  
   - Цена полиса не пересчитывается.

5. **Восстановление**  
   - После исправления ошибки поды `FormTripWithMetrics` запускаются.  
   - Консьюмер начинает читать накопленные сообщения из Kafka (с того места, где остановился).  
   - По мере обработки поездок заполняется БД, публикуются события.  
   - CalculateDrivingCoefficient при следующем ночном запуске обрабатывает накопленные метрики.  
   - BFF начинает отдавать актуальные данные, плашка в приложении исчезает.

### Необходимые компоненты для реализации
- **Kafka с retention 7 дней** для топика `trip_formed`.
- **Мониторинг consumer lag** в Prometheus + алерт при превышении порога (например, > 1000 сообщений).
- **Read replica** DrivingProfileDB для чтения старых данных.
- **Redis** для кэширования коэффициента и прогноза стоимости (TTL 24 часа).
- **Health checks и автоматический перезапуск подов** в Kubernetes.
- **Плашка / уведомление в мобильном приложении**.
- **Retry-механизм** в `FormTripWithMetrics` (при ошибках записи в БД – повтор с экспоненциальной задержкой).

### Ожидаемый результат
- Пользователь продолжает видеть старые (но не пустые) данные с понятным предупреждением.  
- Данные телеметрии и поездок не теряются (очередь в Kafka).  
- После восстановления сервиса все накопленные поездки обрабатываются, система возвращается к штатной работе.  
- Время простоя функциональности прогноза стоимости не критично для бизнеса на период до нескольких дней.
