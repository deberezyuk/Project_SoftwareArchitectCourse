## Защита от DDoS‑атак / всплесков оформления полисов из фронт‑системы

### Контекст
- **Что произошло:** Внешняя фронт‑система (сайт страховщика, партнёрский портал) начинает отправлять аномально большое количество запросов на создание умного полиса (`POST /api/policies`). Это может быть как DDoS‑атака, так и легитимный всплеск (акция, сезонный спрос).
- **Влияние на процесс:** Высокая нагрузка на API Gateway, PolicyManagement Service, БД и другие сервисы. Возможны отказы в обслуживании легитимных клиентов, рост времени ответа, каскадные сбои.

### Основные механизмы отказоустойчивости
- **Rate limiting (throttling)** – ограничение числа запросов от одного клиента (IP, API‑ключ) на уровне External API Gateway.
- **Burst handling** – разрешение кратковременных всплесков с последующим ограничением.
- **Retry с exponential backoff** (на стороне клиента) – легитимная фронт‑система должна повторять запросы с задержкой при получении `429 Too Many Requests`.
- **Очередь асинхронной обработки** (опционально) – синхронный запрос на создание полиса может быть преобразован в асинхронный с возвратом `202 Accepted`, а реальное создание – через Kafka. Но для простоты в данном сценарии оставим синхронный.

### Реакция системы (по шагам)
1. **External API Gateway (Kong)**  
   - Настроен **rate limiting** на endpoint `/api/policies` по комбинации `client_id` (или IP).  
   - Лимит: например, 10 запросов в секунду на одного клиента, burst 20.  
   - При превышении лимита возвращает `429 Too Many Requests` с заголовком `Retry-After: 5`.

2. **Фронт‑система** (клиент)  
   - При получении `429` должна повторить запрос через указанное время (exponential backoff).  
   - Логирует ошибку, но не спамит повторными запросами.

3. **PolicyManagement Service**  
   - Защищён от перегрузки через **connection pool** и **timeout** на входящие запросы.  
   - Использует **bulkhead** (ограничение числа параллельных запросов), чтобы не исчерпать ресурсы.  
   - При превышении внутренних лимитов возвращает `503 Service Unavailable`.

4. **База данных PolicyManagement**  
   - Защищена пулом соединений и таймаутами.  
   - При недоступности сервис возвращает ошибку (не держит соединения бесконечно).

5. **Мониторинг**  
   - Prometheus собирает метрики: количество `429`, время ответа, количество активных запросов.  
   - При превышении порога (например, 1000 `429` за минуту) срабатывает алерт для SRE.

### Необходимые компоненты для реализации
- **External API Gateway (Kong)** с плагином `rate-limiting` (или `rate-limiting-advanced`).
- **Настройка лимитов** для каждого endpoint (например, 10 rps, burst 20).
- **Механизм retry** на стороне фронт‑системы (с экспоненциальной задержкой).
- **Bulkhead / thread pool** в PolicyManagement Service (например, `@Bulkhead` из Resilience4j).
- **Мониторинг** (Prometheus + Grafana) с дашбордами по `429`, latency, error rate.

### Ожидаемый результат
- Легитимные клиенты получают ответ (успех или временная ошибка с инструкцией повторить).  
- При DDoS‑атаке API Gateway отсекает избыточный трафик, не нагружая бэкенд.  
- Система остаётся доступной для остальных операций (просмотр профиля, поездок).  
- Время восстановления после атаки минимально (автоматическое).
