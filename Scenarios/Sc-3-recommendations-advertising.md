# Реакция системы на изменение: добавление рекламы смежных страховых продуктов в рекомендации

**Вероятность изменения:** 50%  
**Домен инициации:** Recommendations (продуктовое требование)  
**Связанные домены:** Recommendations, Notifications, Platform (API Gateway, BFF), Mobile, возможно PolicyManagement (для получения данных клиента)  
**Не затрагиваются:** Telemetry, DrivingAnalytics, Pricing, Support

## 1. Анализ изменения

- В дополнение к рекомендациям по стилю вождения пользователь получает персонализированные рекламные предложения смежных страховых продуктов (например, страхование квартиры, здоровья, путешествий).
- Источник данных о подходящих продуктах – смежные системы страховщика (CRM, продуктовый каталог, системы анализа потребностей).
- Логика генерации рекламного текста инкапсулирована в LLM-платформе, которая уже используется для рекомендаций по вождению. Требуется расширить запрос к LLM дополнительной информацией о клиенте (наличие других полисов, демография, история обращений).
- Рекламные предложения должны отображаться в том же интерфейсе, что и обычные рекомендации (возможно, с визуальным выделением).

## 2. Пошаговый процесс реализации изменений

### 2.1 Recommendations Domain

| Сервис / Компонент | Действие |
|--------------------|----------|
| **RecommendationService** | — Добавить интеграцию с внешними системами страховщика (через API Gateway External) для получения:<br>  &nbsp;&nbsp;– перечня доступных смежных продуктов с условиями,<br>  &nbsp;&nbsp;– данных о текущих полисах клиента,<br>  &nbsp;&nbsp;– скорингов/рекомендаций из аналитических систем.<br>— Модифицировать логику формирования запроса к LLM-платформе: добавить в промпт информацию о смежных продуктах и контексте клиента.<br>— Адаптировать обработку ответа от LLM: извлечь рекламные блоки и объединить с обычными рекомендациями.<br>— Сохранять историю показа рекламы для аналитики (таблица `Recommendation` может быть расширена полем `type`). |
| **База данных** | — Добавить поле `type` в таблицу `DrivingRecommendation` (значения: `driving_tip`, `cross_sell_offer`).<br>— Возможно, добавить таблицу `CrossSellProduct` для кэширования информации о продуктах из внешних систем. |

### 2.2 PolicyManagement Domain (опционально)

| Сервис | Действие |
|--------|----------|
| **PolicyManagement Service** | — Предоставить API для получения списка действующих полисов клиента (уже есть).<br>— Если требуется – расширить данными о типе продукта (домашнее, авто, здоровье). |

### 2.3 Notifications Domain

| Сервис | Действие |
|--------|----------|
| **NotificationService** | — Добавить новый тип уведомления `cross_sell_offer`.<br>— При желании бизнеса отправлять push-уведомления о появлении новых рекламных предложений (с возможностью отписки). |

### 2.4 Platform (API Gateway, BFF)

| Компонент | Действие |
|-----------|----------|
| **External API Gateway** | — Добавить маршруты для вызовов к смежным системам страховщика (с обеспечением безопасности, аутентификации).<br>— Обновить API для мобильного приложения: возвращать расширенный список рекомендаций с типами. |
| **BFF Service** | — Адаптировать агрегацию: передавать на фронт как обычные рекомендации, так и рекламные предложения (возможно, с флагом `isSponsored`). |

### 2.5 Mobile приложение

| Компонент | Действие |
|-----------|----------|
| **Mobile Backend** | — Доработать получение и обработку новых полей в ответе API. |
| **Mobile Frontend** | — Отображать рекламные предложения в отдельном блоке или с пометкой «Реклама».<br>— Добавить возможность перехода по ссылке для оформления продукта (глубинная ссылка на сайт страховщика). |

### 2.6 Другие домены

- **Telemetry, DrivingAnalytics, Pricing, Support** – изменения не требуются.

## 3. Риски и их митигация

| Риск | Митигация |
|------|------------|
| **Конфиденциальность данных клиента** – передача информации о клиенте в LLM-платформу и смежные системы. | Использовать агрегированные/обезличенные данные там, где возможно. Заключить соглашения о защите данных с операторами LLM. |
| **Навязчивость рекламы** – ухудшение пользовательского опыта. | Дать возможность отключения рекламных рекомендаций в настройках. Ограничить частоту показа. |
| **Неточный таргетинг** – предложение нерелевантных продуктов. | Тесно взаимодействовать с аналитической командой страховщика для настройки правил подбора. |
| **Зависимость от внешних систем** – недоступность смежных систем может замедлить или сломать генерацию рекомендаций. | Внедрить таймауты, retry, fallback-логику (если внешняя система недоступна – показывать только рекомендации по вождению). |
| **Увеличение времени ответа** – дополнительные вызовы к внешним API. | Выполнять вызовы параллельно с запросом к LLM (или асинхронно), кэшировать данные о продуктах. |
| **Несогласованность с юридическими требованиями** – маркировка рекламы. | Убедиться, что в интерфейсе рекламные блоки помечены соответствующим образом (например, «Реклама»). |

## 4. Рекомендации по безопасному внедрению

1. **Feature toggle** – внедрить возможность включать/выключать рекламные рекомендации без переразвертывания.
2. **A/B-тестирование** – сначала запустить на небольшой группе пользователей, измерить CTR и влияние на удержание.
3. **Кэширование** – кэшировать ответы от смежных систем (TTL 1 час) для снижения нагрузки и ускорения.
4. **Мониторинг** – отслеживать:
   - время ответа внешних API;
   - долю успешных запросов;
   - количество показанных рекламных блоков;
   - CTR по рекламным предложениям.
5. **Юридическая проверка** – согласовать механизм сбора и передачи данных с юристами.
6. **Тестирование**:
   - Модульное: проверка формирования запроса к LLM.
   - Интеграционное: имитация ответов внешних систем.
   - Нагрузочное: симуляция пикового трафика к внешним API.

## 5. Заключение

Изменение требует доработки в первую очередь **RecommendationService** (интеграция с внешними системами, расширение запроса к LLM) и **мобильного фронта** (отображение рекламных блоков). Notifications и API Gateway затрагиваются незначительно. Модифицируемость оценивается как **средняя** (CPI ≈ 0.3), основные риски связаны с безопасностью данных и зависимостью от внешних систем. При использовании feature toggles и кэширования риски управляемы.
