## Недоступность сервисов домена Support (Appointment и SensorManagement)

### Контекст
- **Что произошло:** Один или оба сервиса домена Support (`AppointmentService`, `SensorManagementService`) стали недоступны (сбой кода, исчерпание ресурсов, отказ узлов Kubernetes).
- **Влияние на процесс:**  
  - **AppointmentService** – запись на встречи (асинхронная) временно недоступна. Клиенты не могут создать новую встречу или подтвердить существующую.  
  - **SensorManagementService** – синхронные вызовы (например, мастер ТО сканирует датчик) возвращают ошибки. Мастер не может завершить установку датчика, что ухудшает пользовательский опыт.

### Основные механизмы отказоустойчивости
- **Асинхронная обработка через Kafka** – для AppointmentService: запросы на создание встреч накапливаются в очереди, не теряются.
- **Retry с exponential backoff** – для синхронных вызовов SensorManagementService.
- **Graceful degradation на уровне BFF** – возврат понятной ошибки мастеру ТО.
- **Горизонтальное масштабирование** сервисов (минимум 2 реплики).

### Реакция системы (по шагам)

#### Для AppointmentService (асинхронный)
1. **AppointmentService** недоступен.  
2. **BFF** (при попытке создать встречу) публикует событие в Kafka (топик `appointment_requests`), не дожидаясь ответа.  
3. **Kafka** накапливает события.  
4. После восстановления сервиса, консьюмер (`AppointmentService`) обрабатывает накопленные события.  
5. **Пользователь** не видит ошибки при создании встречи – запрос принят, уведомление о подтверждении придёт позже.

#### Для SensorManagementService (синхронный)
1. **Мастер ТО** в приложении пытается зафиксировать установку датчика.  
2. **BFF** вызывает `SensorManagementService` по HTTP.  
3. При ошибке (таймаут, 5xx) BFF выполняет retry (3 попытки с задержкой 1,2,4 сек).  
4. Если все попытки неудачны, BFF возвращает мастеру ошибку: «Сервис временно недоступен, попробуйте позже».  
5. Мастер видит сообщение и может повторить попытку вручную.  
6. **Дополнительно:** при повторяющихся ошибках BFF может публиковать событие в Kafka для отложенной обработки (но это меняет UX, т.к. мастер не получит мгновенного подтверждения). В текущей реализации – синхронный отказ.

### Необходимые компоненты для реализации
- **Kafka топик** `appointment_requests` с увеличенным retention.
- **Retry-механизм с exponential backoff** в BFF для вызовов SensorManagementService.
- **Мониторинг доступности сервисов** (Prometheus + алерты).
- **Горизонтальное масштабирование** AppointmentService и SensorManagementService (минимум 2 реплики).
- **Health checks** в Kubernetes для автоматического перезапуска подов.

### Ожидаемый результат
- Для AppointmentService – асинхронная очередь гарантирует, что запросы не теряются. Пользователь не видит ошибок.
- Для SensorManagementService – мастер видит понятную ошибку и может повторить действие. При кратковременном сбое retry решает проблему.
- Система не требует ручного вмешательства для восстановления.
