## Недоступность BFF‑сервиса

### Контекст
- **Что произошло:** Все реплики BFF‑сервиса (Backend for Frontend) стали недоступны (сбой кода, исчерпание ресурсов, ошибка развертывания, отказ узлов Kubernetes).
- **Влияние на процесс:** Мобильное приложение не может получить агрегированные данные для отображения пользовательского интерфейса (профиль, поездки, рекомендации). API Gateway возвращает ошибки 5xx. Фоновые процессы (телеметрия, расчёт коэффициентов) не затрагиваются.

### Основные механизмы отказоустойчивости
- **Горизонтальное масштабирование BFF** – минимум 2 реплики, распределение нагрузки через Ingress.
- **Health checks и автоматический restart** – Kubernetes перезапускает упавшие поды.
- **Graceful degradation на клиенте** – мобильное приложение отображает кэшированные данные и информационное сообщение.
- **Мониторинг и алертинг** – быстрое обнаружение отказа.

### Реакция системы (по шагам)
1. **Kubernetes**  
   - Health check (readiness/liveness) BFF проваливается.  
   - Поды BFF автоматически перезапускаются (если возможно) или не получают трафик.  
   - Если все реплики недоступны, Ingress перестаёт направлять запросы на BFF.

2. **API Gateway (Kong)**  
   - Обнаруживает, что все эндпоинты BFF недоступны (503).  
   - Возвращает мобильному приложению ошибку 503 с телом `{"error": "Service temporarily unavailable"}`.

3. **Мобильное приложение**  
   - Получает ошибку 503.  
   - Отображает кэшированные данные (последний успешный ответ из локального хранилища).  
   - Показывает плашку: «Сервис временно недоступен, данные могут быть неактуальны».  
   - Периодически повторяет запрос (например, каждые 30 секунд).

4. **Восстановление**  
   - После восстановления хотя бы одной реплики BFF, Ingress снова начинает направлять трафик.  
   - Мобильное приложение при следующем успешном запросе получает актуальные данные и убирает плашку.

### Необходимые компоненты для реализации
- **Минимум 2 реплики BFF** в Kubernetes (с распределением нагрузки).
- **Readiness/liveness probes** для автоматического перезапуска.
- **Настройка Ingress** (например, NGINX или Kong) с таймаутами и retry.
- **Локальное кэширование на клиенте** (мобильное приложение) – сохранение последнего ответа.
- **Мониторинг (Prometheus + Grafana)** – отслеживание количества реплик BFF, ошибок 5xx.
- **Алерт** в SRE о недоступности BFF (если все реплики не восстанавливаются за N минут).

### Ожидаемый результат
- Пользователь видит не пустой экран, а кэшированные данные с понятным предупреждением.
- Система автоматически восстанавливается после перезапуска подов или масштабирования.
- Время простоя BFF минимизировано за счёт горизонтального масштабирования и быстрого перезапуска.
