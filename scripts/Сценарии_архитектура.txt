Сценарий 1 - Оформление умного полиса в системе

1. Внешняя фронт-система отправляет синхронный HTTP-запрос (POST) с данными о клиенте, автомобиле и полисе в External API Gateway.
2. API Gateway направляет запрос в Сервис полис (Policy Service) – единую точку входа для всех операций с полисами.
3. Сервис полис выполняет следующие шаги в рамках одной транзакции (или саги):
4. Синхронно вызывает Сервис страхователь для создания/получения записи о клиенте. Возвращается policyholderId.
5. Синхронно вызывает Сервис авто для создания записи об автомобиле (связывая с policyholderId). Возвращается vehicleId.
6. Создаёт запись о полисе в своей БД, связывая с полученными идентификаторами.
7. После успешного сохранения Сервис полис публикует событие PolicyCreated в топик Kafka (например, policy-events).
8. Сервис профиля вождения (DrivingAnalytics) подписан на это событие. При получении он создаёт пустой профиль вождения для данного клиента/автомобиля со статусом "ожидает авторизации".
9. Сервис уведомлений также может подписаться на событие и отправить клиенту приветственное сообщение или инструкцию по авторизации через External API GW через Омниканальную платформу
10. Сервис полис возвращает синхронный ответ через API Gateway во внешнюю систему с подтверждением создания полиса и данными для дальнейшей авторизации.

Сценарий 3 - сбор телеметрии и формирование поездок
датчик телеметрии отправляет данные телеметрии в контур компании
первым делом пакеты данных телеметрии попадают в изолированный шлюз телеметрии
оттуда пакеты телеметрии маршрутизируются в топик отдельного кластера Kafka, развернутого под IoT в контуре страховщика
GatherTelemetry Service (часть Telemetry Domain) получает пакеты телеметрии и сохраняет их в БД для телеметрии в привязке к id датчика
FormTripsTelemetry Service читает данные из БД раз в N минут/секунд и агрегирует точки телеметрии в поездки
данные сервис также рассчитывает базовые метрики стиля вождения для каждой поездки
записывая их в отдельную таблицу БД в привязке к поездкам и отправляя события новой поездки в корп кластер Kafka (уже не для телеметрии)

Сценарий 7 - рекомендации. как данные из БД DrivingAnalytics должны кочевать для рекомендаций, чтобы не делать запросы в БД напрямую. Если пользователь в настройках включает необходимость в рекомендациях, то может выбрать частотность рекомендаций: раз в неделю/месяц. Джоба в профиле клиента инициирует событие для необходимости рекомендации, сервис рекомендации (как) получает данные по поездкам пользователя, вместе с метриками и данными GPS, и после агрегации отправляет пакетно в LLM-платформу для создания рекомандаций. при этом, под капотом LLM-платформы остаются нюансы. на выходе рекомендация сохраняется в БД, создается событие для уведомления, которое подхватывает Notification сервис и отправляет по выбранным каналам связи.
