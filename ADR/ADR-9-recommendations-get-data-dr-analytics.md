# ADR-9: Способ получения данных из DrivingAnalytics для формирования рекомендаций

## Контекст
Сервис `RecommendationService` (домен Recommendations) периодически формирует персонализированные рекомендации для клиентов на основе их стиля вождения за прошедший месяц. Для этого ему необходимы:
- История метрик стиля вождения (количество резких торможений, ускорений, превышений скорости и т.п.) по каждому клиенту за месяц.
- История коэффициентов стиля вождения (для понимания динамики).

Данные хранятся в БД домена DrivingAnalytics. Необходимо выбрать способ доступа `RecommendationService` к этим данным, обеспечивающий:
- Производительность (быстрое извлечение большого объёма данных для тысяч клиентов).
- Надёжность (отсутствие влияния на работу основных сервисов).
- Соответствие принципам микросервисной архитектуры (инкапсуляция, независимость).

## Решение с обоснованием
**Используем прямой доступ `RecommendationService` к read replica БД домена DrivingAnalytics.**

### Детали реализации
- `RecommendationService` подключается к **read replica** PostgreSQL, на которой развёрнута БД DrivingAnalytics.
- Для извлечения данных используются предварительно созданные представления (views) или прямые SQL-запросы к таблицам поездок, метрик и профилей вождения.
- Доступ осуществляется с использованием отдельной учётной записи, имеющей права только на чтение и только на необходимые таблицы/представления.

**Почему это решение:**
- **Производительность**: чтение больших объёмов данных (например, за месяц для 50 000 клиентов) напрямую из реплики быстрее, чем через последовательные синхронные вызовы API сервиса.
- **Минимальная нагрузка на сервис DrivingAnalytics**: реплика БД не влияет на производительность основной записи (write) и работу сервиса.
- **Согласованность**: данные на реплике отстают от мастера на несколько секунд, что для месячного отчёта некритично.
- **Простота реализации**: не требует создания нового API, версионирования и поддержки.
- **Безопасность**: права доступа ограничены чтением, что исключает случайные изменения данных.

## Рассматриваемые альтернативы

### Альтернатива 1: Синхронный вызов API сервиса DrivingAnalytics
- **Описание**: `RecommendationService` вызывает REST-API сервиса `DrivingAnalytics` для получения агрегированных данных по клиенту.
- **Плюсы**: соблюдается инкапсуляция, сервис может предоставлять только необходимые данные, легко версионировать.
- **Минусы**:  
  - Добавляет сетевую задержку (каждый запрос требует HTTP-вызова).  
  - Создаёт дополнительную нагрузку на сервис `DrivingAnalytics`, особенно при массовой обработке (50 000 запросов за месяц).  
  - Требует разработки и поддержки API.
- **Отклонена** как избыточно сложная и потенциально менее производительная.

### Альтернатива 2: Асинхронная выгрузка через Kafka с накоплением в БД Recommendations
- **Описание**: После ночного расчёта коэффициента `DrivingAnalytics` публикует события с агрегированными данными (метрики, коэффициенты) за месяц. `RecommendationService` подписывается на эти события и сохраняет их в своей БД. При необходимости формирования рекомендации использует уже готовые данные.
- **Плюсы**:  
  - Данные подготавливаются заранее, время формирования рекомендации минимально.  
  - Полная развязка сервисов по времени.
- **Минусы**:  
  - Сложность синхронизации: нужно гарантировать, что все данные за месяц опубликованы до момента формирования рекомендации.  
  - Дублирование данных в БД Recommendations (хранение агрегатов).  
  - Требуется поддерживать сложную логику обработки событий и идемпотентность.
- **Отклонена** как избыточная для текущих требований, хотя может быть рассмотрена в будущем при росте масштаба.

### Альтернатива 3: Прямой доступ к master-БД
- **Описание**: `RecommendationService` читает данные напрямую из master-инстанса БД DrivingAnalytics.
- **Плюсы**: минимальная задержка данных (актуальны на момент запроса).
- **Минусы**:  
  - Создаёт дополнительную нагрузку на master-БД, что может ухудшить производительность записи.  
  - Риск блокировок при тяжёлых аналитических запросах.
- **Отклонена** в пользу использования read replica, что уже было предусмотрено в ADR-5.

## Последствия
- **Разработка**: необходимо создать отдельную учётную запись для чтения в БД DrivingAnalytics и настроить подключение в `RecommendationService`.  
- **Инфраструктура**: требуется, чтобы read replica БД DrivingAnalytics была доступна для сервисов в домене Recommendations (network policy).  
- **Мониторинг**: добавить метрики времени выполнения SQL-запросов, объёма передаваемых данных, ошибок доступа.  
- **Согласованность**: учесть, что на реплике может быть лаг (до нескольких секунд). Для формирования рекомендаций за месяц это некритично.  
- **Безопасность**: ограничить права учётной записи только на необходимые таблицы (trips, driving_metrics, driving_profile_history).  
- **Масштабирование**: если нагрузка на реплику станет высокой, можно добавить дополнительные read replica и балансировать запросы между ними.

Решение принято на основе баланса между производительностью, простотой и соблюдением архитектурных принципов. В будущем, при усложнении логики доступа, может быть добавлен слой API, но на текущем этапе прямое чтение из реплики является оптимальным.
