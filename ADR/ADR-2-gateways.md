# ADR-2: Архитектура API Gateway

## Контекст
Система умного автострахования включает несколько доменов, в системе комбинация микросервисной и событийной архитектуры. Запросы поступают от:
- **Внешних клиентов**: мобильное приложение, внешние фронт-системы страховщика.
- **Внутренних сервисов**: синхронные вызовы между сервисами разных доменов.

Необходимо определить:
- Сколько API Gateway использовать.
- Какие функции возложить на шлюзы (маршрутизация, аутентификация, rate limiting, логирование).
- Будет ли использоваться API Gateway для вызовов между сервисами одного домена.

## Решение с обоснованием
**Используем два типа API Gateway:**

1. **External API Gateway** – единая точка входа для всех внешних запросов (мобильное приложение, внешние фронт-системы) как в систему, так и из системы.  
   - **Функции**:  
     - Приём HTTPS-запросов с валидацией TLS;
     - Локальная валидация JWT (проверка подписи, срока действия, claims);
     - Маршрутизация запросов к соответствующим внутренним сервисам (BFF, Policy Management Service, другие публичные API);  
     - Rate limiting для защиты от DDoS; 
     - Централизованное логирование и сбор метрик для внешнего трафика. 
   - **Обоснование**: отдельный внешний шлюз обеспечивает безопасность периметра, унифицирует обработку аутентификации и позволяет изменять внутреннюю структуру без влияния на клиентов.

2. **Internal API Gateway** – используется для синхронных вызовов **между сервисами разных доменов**, кроме BackendForFrontend-сервиса. 
   - **Функции**:  
     - Централизованное управление аутентификацией и авторизацией внутренних вызовов (проверка JWT или служебных токенов).  
     - Единая точка для политик retry, timeout, circuit breaker.  
     - Унификация протоколов (если сервисы используют разные протоколы).  
   - **Обоснование**: Internal API Gateway снижает связанность между доменами, позволяет централизованно управлять сквозными требованиями (наблюдаемость, безопасность) и упрощает рефакторинг. Однако он добавляет дополнительный сетевой hop, поэтому его использование ограничивается только вызовами между разными доменами (там, где задержка не критична). Внутри одного домена сервисы вызывают друг друга напрямую, что соответствует подходам микросервисной архитектуры и снижает latency.

**Почему не один универсальный шлюз?**  
Разделение на внешний и внутренний позволяет применять разные политики безопасности (внешний шлюз жёстче контролирует входящий трафик), масштабировать их независимо и избегать смешения ответственности.

## Рассматриваемые альтернативы

### Альтернатива 1: Только External API Gateway (без Internal)
- **Плюсы**: проще архитектура, меньше компонентов.  
- **Минусы**: все внутренние вызовы между сервисами идут напрямую, что увеличивает связанность и усложняет внедрение сквозных политик (логирование, авторизация) для каждого сервиса.  
- **Отклонена**, так как не обеспечивает централизованного контроля межсервисного взаимодействия.

### Альтернатива 2: Единый универсальный шлюз для всех запросов (внешних и внутренних)
- **Плюсы**: единый компонент, проще управлять.  
- **Минусы**: смешивает трафик разной природы, что может привести к проблемам безопасности (внутренние вызовы могут случайно стать доступными извне). Требует сложной маршрутизации и может стать узким местом.  
- **Отклонена** из-за риска утечки внутренних API и усложнения конфигурации.

### Альтернатива 3: Использование Service Mesh вместо Internal API Gateway
- **Плюсы**: прозрачное добавление наблюдаемости, безопасности (mTLS) и трафик-менеджмента без отдельного компонента-шлюза.  
- **Минусы**: требует внедрения дополнительной инфраструктуры (Istio, Linkerd), команда не знакомы с этой технологией.  
- **Отложена** как возможное будущее улучшение; на начальном этапе выбран Internal API Gateway как более простой и знакомый вариант.

## Последствия
- **Разработка**: необходимо реализовать два шлюза (или использовать готовые решения, например, Kong/Spring Cloud Gateway);
- **Безопасность**: на оба API Gateway настроена строгая валидация JWT;
- **Мониторинг**: логи и метрики собираются отдельно для внешнего и внутреннего трафика;
- **Масштабируемость**: оба шлюза горизонтально и независимо масштабируются;
- **Стоимость**: добавление внутреннего шлюза увеличивает количество компонентов и требует дополнительной настройки, но окупается за счёт упрощения управления политиками.
