# ADR-1: Обоснование функциональной декомпозиции системы умного автострахования с оценкой модифицируемости

## 1. Методология оценки модифицируемости

Для количественной и качественной оценки модифицируемости используется:

- **Коэффициент распространения изменений (CPI)** – среднее количество сервисов, которые необходимо изменить при типовом бизнес-изменении (добавление новой метрики, изменение правила расчёта коэффициента, новый канал уведомлений), делённое на общее количество сервисов в выбранной декомпозиции.
- **Связность (cohesion)** – насколько тесно связаны функции внутри одного сервиса.
- **Сцепление (coupling)** – насколько изменение в одном сервисе требует изменения в другом.
- **Независимость масштабирования** и **сложность развёртывания**.

**Целевые значения CPI:**  
- < 0,2 – отлично  
- 0,2–0,35 – хорошо  
- \> 0,5 – плохо

## 2. Контекст

Система умного автострахования должна поддерживать рост с 1 000 до 100 000 клиентов, частые изменения бизнес-логики (расчет метрик, коэффициента стиля вождения, ценообразование, агрегация данных для рекомендаций) и независимую работу нескольких команд в будущем. Архитектурный стиль – **микросервисы** с асинхронным взаимодействием через Kafka и синхронными вызовами через Internal API Gateway.

## 3. Выбранный вариант декомпозиции (финальный)

### 3.1 Состав сервисов и их функциональность

#### Telemetry Domain
| Сервис | Краткое описание функциональности |
|--------|----------------------------------|
| **Telemetry Gateway** | Внешний шлюз для приёма телеметрии по MQTT, изоляция по требованиям ИБ. |
| **Kafka IoT (отдельный кластер)** | Очередь сообщений для сырых данных телеметрии (изолирована от корпоративной Kafka). |
| **GatherTelemetry Service** | Потребляет сообщения из Kafka, сохраняет сырые точки телеметрии в БД (Postgre с TimescaleDB + PostGIS). |
| **FormTripsTelemetry Service** | Периодически читает данные из БД, детектирует поездки, рассчитывает базовые метрики, сохраняет файлы с геоданными и нарушениями в MinIO, публикует событие `trip_formed` в корпоративную Kafka. |

#### DrivingAnalytics Domain
| Сервис | Краткое описание функциональности |
|--------|----------------------------------|
| **FormTripWithMetrics Service** | Подписывается на `trip_formed`, загружает файлы из MinIO, рассчитывает сложные метрики стиля вождения, сохраняет метрики в БД, публикует `trip_metrics_calculated`. |
| **CalculateDrivingCoefficient Service** | Ночной пакетный процесс: читает из БД поездки за сутки с метриками, получает текущий коэффициент, вычисляет новый (с учётом весов), обновляет профиль вождения и публикует `driving_coefficient_updated`. |
| **DrivingProfile Service** | Синхронный онлайн-сервис: предоставляет возможность получить или обновить профиль вождения (коэффициент, историю) по запросу. |

**Общая БД** (PostgreSQL с read replica) – для поездок, метрик, профилей. Используется CQRS: запись в master, чтение аналитики с реплики.

#### Pricing Domain
| Сервис | Краткое описание функциональности |
|--------|----------------------------------|
| **CalculateInsurancePolicyPrice Service** | Подписывается на `driving_coefficient_updated`, синхронно получает данные клиента, авто, полиса из PolicyManagement, через API Gateway запрашивает прогнозную стоимость у внешней системы тарификации, при изменении публикует `insurance_price_updated`. |

#### PolicyManagement Domain
| Сервис | Краткое описание функциональности |
|--------|----------------------------------|
| **PolicyManagement Service** | Оркестратор операций с полисами: создание, изменение статуса, отмена динамического ценообразования, обновление полиса в страховой учётной системе. |
| **Insurer Service** | Управление данными клиентов (страхователей): создание, обновление, поиск. |
| **Vehicle Service** | Управление данными автомобилей: vin, марка, модель, год выпуска, привязка к клиенту. |

**Общая БД** – для полисов, клиентов, автомобилей (сервисы разделены для независимого развертывания и масштабирования).

#### Recommendations Domain
| Сервис | Краткое описание функциональности |
|--------|----------------------------------|
| **Recommendation Service** | Ежедневно формирует очередь клиентов, читает метрики и файлы нарушений из DrivingAnalytics (read replica + MinIO), агрегирует топ‑нарушений по геозонам, формирует сжатый JSON-запрос и отправляет в LLM-платформу через External API Gateway, потребляет ответ из Kafka, сохраняет рекомендации в свою БД. |

#### Notification Domain
| Сервис | Краткое описание функциональности |
|--------|----------------------------------|
| **Notification Service** | Подписывается на события, Формирует push/SMS/email уведомления через External API Gateway (омниканальная платформа). Хранит настройки предпочтений клиентов. |

#### Support Domain
| Сервис | Краткое описание функциональности |
|--------|----------------------------------|
| **Support Service** | Обработка обращений клиентов (текстовые и звонки), эскалация, ответы. |
| **Appointment Service** | Запись клиентов на установку/замену датчика, управление слотами, подтверждение мастером ТО, публикация событий `appointment_created`, `appointment_confirmed`. |
| **SensorManagement Service** | Управление датчиками: регистрация, привязка к автомобилю, проверка идемпотентности, отслеживание статуса, публикация `sensor_installed`. |

Каждый сервис имеет собственную БД.

#### Platform Domain
| Компонент | Краткое описание функциональности |
|-----------|----------------------------------|
| **MinIO S3** | Хранение больших файлов: геоданных, нарушений, агрегированных метрик. |
| **Internal API Gateway** | Синхронные вызовы между сервисами разных доменов (HTTPS, централизованные политики). |
| **External API Gateway** | Вход для внешних систем (мобильное приложение, фронт-системы). Валидация JWT, rate limiting, маршрутизация. |
| **BFF (Backend for Frontend)** | Агрегация данных для мобильного приложения, вызывает сервисы напрямую (минуя Internal API Gateway). |
| **Kafka (корпоративный)** | Центральная шина событий. |
| **Keycloak** | Аутентификация и управление ролями (JWT, 2FA, интеграция с корпоративным IAM). |

### 3.2 Оценка модифицируемости

- **CPI ≈ 0,15–0,25** – хороший показатель.
- **Связность** – высокая внутри сервисов (каждый решает чёткую задачу).
- **Сцепление** – низкое за счёт событий через Kafka и использования API Gateway.
- **Независимое масштабирование** – поддерживается для каждого сервиса.
- **Независимое развертывание** – каждый сервис имеет свой CI/CD.

## 4. Альтернативные варианты декомпозиции

### 4.1 Альтернатива 1: Консолидированная (укрупнённая)

**Состав сервисов** (всего 7):

| Домен | Сервис | Функциональность (кратко) |
|-------|--------|---------------------------|
| Telemetry | `TelemetryService` | Приём телеметрии + детектирование поездок + базовые метрики + запись в MinIO. |
| DrivingAnalytics | `DrivingAnalyticsService` | Расчёт сложных метрик + ночной расчёт коэффициента + синхронные запросы профиля. |
| Pricing | `PricingService` | Расчёт цены полиса. |
| PolicyManagement | `PolicyManagementService` | Всё управление полисами, клиентами, автомобилями. |
| Recommendations | `RecommendationsService` | Формирование рекомендаций (без изменений). |
| Notification | `NotificationService` | Уведомления (без изменений). |
| Support | `SupportService` | Обращения + встречи + управление датчиками. |

**Оценка модифицируемости:** CPI ≈ 0,5–0,7 (плохо). Изменения затрагивают весь домен, невозможно масштабировать компоненты по отдельности.

### 4.2 Альтернатива 2: Экстремальная (атомарная)

**Пример разбиения** (более 30 сервисов):

| Исходный сервис | Разбиение |
|----------------|-----------|
| `FormTripsTelemetry` | `TripDetector`, `BasicMetricsCalculator`, `MinIOWriter`, `TripEventPublisher`. |
| `FormTripWithMetrics` | `TripConsumer`, `AdvancedMetricsCalculator`, `MetricsPersister`, `MetricsEventPublisher`. |
| `CalculateDrivingCoefficient` | `CoefficientCalculator`, `ProfileUpdater`, `HistoryWriter`. |
| `RecommendationService` | `Scheduler`, `DataAggregator`, `LLMClient`, `ResponseConsumer`. |

**Оценка модифицируемости:** CPI ≈ 0,05–0,1 (отлично). Однако резко возрастает сложность координации (распределённые транзакции, множество сетевых вызовов), операционная сложность (мониторинг 30+ сервисов), требуется зрелая инфраструктура (service mesh). Для текущего масштаба избыточно.

### 4.3 Альтернатива 3: Гибридная (по частоте изменений и нагрузке)

**Состав сервисов** (10–12):

| Сервис | Функциональность |
|--------|------------------|
| `GatherTelemetry` | Без изменений. |
| `TripProcessingService` | Объединяет `FormTripsTelemetry` и `FormTripWithMetrics` (обе работают с поездками). |
| `CalculateDrivingCoefficient` | Без изменений. |
| `CustomerDataService` | Объединяет `Insurer` и `Vehicle` (редко меняются). |
| `PolicyManagementService` | Только управление полисами (без клиентов и авто). |
| `DrivingProfile` | Объединён с `PolicyManagementService` (сильная связь по данным). |
| Остальные сервисы (`Pricing`, `Recommendations`, `Notification`, `Support`, `Appointment`, `SensorManagement`) – без изменений. |

**Оценка модифицируемости:** CPI ≈ 0,2–0,3 (хорошо). Меньше сервисов, чем в текущем варианте, но появляется риск связанности (например, `DrivingProfile` с `PolicyManagement`). Может быть рассмотрена как эволюционный шаг в будущем.

| **Сложность эксплуатации** | Средняя | Низкая | Высокая | Средняя |
| **Независимое масштабирование** | Да | Нет | Да | Частично |
| **Подходит для частых изменений** | Да | Нет | Да | Да |

## 6. Вывод

**Текущий вариант декомпозиции признан оптимальным.** Он обеспечивает:
- Хорошую модифицируемость (CPI 0,15–0,25).
- Управляемое количество сервисов (15).
- Возможность независимого масштабирования и развертывания.
- Соответствие микросервисным принципам.

Альтернативные варианты либо снижают модифицируемость (укрупнённый), либо чрезмерно усложняют архитектуру (экстремальный), либо вносят риски связанности (гибридный). Решение принято с учётом текущих требований и планов роста.
