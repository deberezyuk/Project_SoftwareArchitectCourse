# ADR-11: Организация передачи данных в LLM-платформу для генерации рекомендаций

## Контекст
`RecommendationService` (домен Recommendations) формирует для клиента набор данных, необходимых для генерации текста рекомендации:
- Агрегированные метрики стиля вождения за месяц (из БД DrivingAnalytics).
- Список неаккуратных маневров с привязкой к геолокации (из MinIO).

Эти данные передаются во внешнюю LLM-платформу по **синхронному HTTP REST** вызову. Платформа возвращает результат **асинхронно**, публикуя ответ в указанный клиентом топик Kafka.

**Ограничения:**
- Максимальный размер тела HTTP-запроса – **1 МБ** (установлен на уровне API Gateway / балансировщика).
- Время синхронного ожидания ответа от платформы – до 10 секунд (сама платформа отвечает немедленно, но генерация происходит позже).
- Объём исходных данных для клиента может составлять несколько мегабайт (до 100+ поездок с геоданными).

Необходимо выбрать способ подготовки и передачи данных, который:
- Гарантирует попадание в лимит 1 МБ после сжатия.
- Обеспечивает достаточную информативность для формирования качественных рекомендаций.
- Минимизирует задержки и нагрузку на сеть.

## Решение с обоснованием
**Используем подход: агрегация + выбор топ-N нарушений + сжатие gzip.**

### Детали реализации
1. **Агрегация данных**  
   - Из БД DrivingAnalytics извлекаются агрегированные метрики за месяц: общее количество нарушений по типам, средние значения, общая дистанция, количество поездок.  
   - Из MinIO для каждой поездки загружается файл с детальными нарушениями (координаты, тип).  
   - Все нарушения за месяц группируются по геозонам (например, с использованием кластеризации или сетки 0.001° ≈ 100 м) и по типам.  
   - Для каждой зоны вычисляется **вес** нарушения (задан бизнес-правилами, например, превышение скорости ×5, резкое торможение ×3).  
   - Зоны сортируются по суммарному весу, выбираются топ‑N (например, 10–20) самых значимых зон.  
   - Для каждой выбранной зоны формируется запись: координаты (центр зоны), тип(ы) нарушений, количество раз, краткое текстовое описание.

2. **Формирование JSON-объекта**  
3. **Сжатие и отправка**  
   - JSON сериализуется и сжимается gzip (заголовок `Content-Encoding: gzip`).  
   - Ожидаемый размер сжатого JSON для типичного клиента (50 поездок, 20 зон) – **100–300 КБ**, что укладывается в лимит.  
   - В случае, если даже после агрегации размер превышает 1 МБ (например, клиент имеет 500 поездок), можно уменьшить N (количество зон) или применить более жёсткую фильтрацию (например, объединять зоны с низким весом в общую категорию "прочие нарушения").

4. **Обработка ответа**  

**Обоснование выбора:**
- **Соблюдение лимита 1 МБ**: агрегация и выбор топ-зон сокращают объём данных на 90–95% по сравнению с передачей всех деталей.
- **Информативность**: топ-зоны покрывают наиболее значимые нарушения, что достаточно для формирования содержательной рекомендации (например, "на перекрёстке X вы часто превышаете скорость").
- **Эффективность**: сжатие gzip дополнительно уменьшает размер, снижая сетевой трафик.
- **Надёжность**: асинхронный ответ через Kafka исключает потерю результата и развязывает по времени.

## Рассматриваемые альтернативы

### Альтернатива 1: Передача всех данных (без агрегации) с использованием multipart/form-data
- **Плюсы**: платформа получает максимальную информацию.
- **Минусы**: объём запроса может превысить 1 МБ даже после сжатия; требуется разбиение на части, что усложняет как отправку, так и обработку на стороне LLM.
- **Отклонена** из-за несоответствия лимиту и высокой сложности.

### Альтернатива 2: Отправка ссылки на объект в MinIO
- **Описание**: вместо передачи данных в теле запроса `RecommendationService` сохраняет подготовленный JSON в MinIO и передаёт LLM-платформе URL объекта. Платформа загружает данные по ссылке.
- **Плюсы**: тело запроса остаётся маленьким, не зависит от объёма данных.
- **Минусы**: требует поддержки со стороны LLM-платформы (дополнительный HTTP-запрос к MinIO). Увеличивает время обработки.
- **Отложена** как запасной вариант на случай, если даже агрегированные данные не будут укладываться в 1 МБ после сжатия.

### Альтернатива 3: Разделение на несколько последовательных запросов (chunking)
- **Плюсы**: позволяет передать все данные.
- **Минусы**: сложность синхронизации (нужно собирать ответы), увеличение числа вызовов.
- **Отклонена** как избыточно сложная.

### Альтернатива 4: Передача данных в виде статистик (без геолокации)
- **Плюсы**: минимальный размер.
- **Минусы**: потеря привязки к локациям делает рекомендации общими ("вы часто превышаете скорость") вместо конкретных ("на трассе МКАД"). Снижается ценность для клиента.
- **Отклонена** как не удовлетворяющая требованию привязки к локациям.

## Последствия
- **Разработка**:
  - Реализовать алгоритм агрегации и выбора топ-зон (веса, кластеризация, группировка) на стороне Recommendations Service.
  - Добавить сжатие gzip в HTTP-клиенте.
  - Обеспечить идемпотентность сохранения рекомендаций (проверка, что рекомендация за месяц уже не сохранена).
- **Инфраструктура**:
  - Убедиться, что API Gateway разрешает передачу сжатых тел и не ограничивает размер более 1 МБ (при необходимости увеличить лимит до 2 МБ, но это потребует согласования).
  - Создать топик `recommendation.responses` с retention, достаточным для покрытия возможных задержек.
- **Мониторинг**:
  - Отслеживать размеры запросов (до сжатия и после), время ответа платформы, количество повторных попыток.
  - При превышении лимита 1 МБ (даже после агрегации) генерировать алерт для анализа и настройки параметров (например, уменьшить N или включить альтернативный путь через MinIO).
- **Масштабируемость**:
  - Горизонтальное масштабирование воркеров `RecommendationService` увеличивает параллелизм отправки запросов.
  - Консьюмер ответов может работать на тех же репликах (каждая реплика получает часть сообщений из Kafka).

Решение принято с учётом жёсткого ограничения на размер запроса и необходимости сохранить ценную информацию о локациях нарушений. Оно позволяет уложиться в лимит, обеспечивая достаточную детализацию для формирования полезных рекомендаций.
