# ADR-3: Выбор инструмента для аутентификации и авторизации

## Контекст
Система умного автострахования требует:
- Аутентификации пользователей (страхователи, сотрудники ТО) с поддержкой двухфакторной аутентификации (2FA) через SMS;
- Разграничения доступа на основе ролей (`client`, `technician`). Роль может назначаться либо по пригласительной ссылке (при оформлении полиса), либо выбираться пользователем при регистрации;
- Выдачи JWT-токенов для доступа к API. Токены должны валидироваться на уровнях:
  - External API Gateway – локальная проверка подписи для внешних запросов;
  - Internal API Gateway – валидация JWT для межсервисных вызовов между разными доменами;
  - Внутри одного домена – сервисы самостоятельно валидируют JWT (при необходимости);
- Интеграции с корпоративным IAM (в компании уже развёрнут Keycloak);
- Масштабируемости и отказоустойчивости (Keycloak кластеризован централизованно).

## Решение с обоснованием
**Используем корпоративный Keycloak** как центральный Identity and Access Management (IAM) компонент.

**Обоснование:**
- Keycloak уже развёрнут в компании, что исключает затраты на внедрение нового решения и упрощает интеграцию с существующими сервисами;
- Поддерживает все необходимые протоколы (OAuth2, OIDC) и предоставляет встроенные механизмы 2FA через SMS (SPI) – не требуется разработка кастомного адаптера;
- Позволяет хранить роли как атрибуты пользователя (realm-роли или клиентские роли), что обеспечивает гибкость при назначении прав;
- Может выступать в роли провайдера JWT; сервисы и шлюзы могут локально валидировать токены, используя публичный ключ Keycloak;
- Обеспечивает высокую доступность (централизованный кластер) и масштабируемость.

**Детали реализации:**
- **Аутентификация**: мобильное приложение использует OAuth2 Authorization Code Flow с PKCE; Keycloak через отдельный адаптер взаимодействует с SMS-провайдером для формирования кода авторизации.
- **Роли**: хранятся в Keycloak как realm-роли. Назначение ролей:
  - При создании полиса (сценарий 1) Notification Service генерирует одноразовую ссылку, содержащую роль `client`. При переходе Keycloak создаёт пользователя с этой ролью.
  - При самостоятельной регистрации пользователь выбирает роль из списка (`client` или `technician`); Keycloak фиксирует выбранную роль.
  - Администратор может вручную изменить роль пользователя в Keycloak (по заявке).
- **Валидация JWT**:
  - External API Gateway проверяет JWT локально (по публичному ключу Keycloak) и передаёт в BFF заголовки `X-User-ID`, `X-User-Roles`.
  - Internal API Gateway также валидирует JWT (для запросов между доменами) и может пробрасывать те же заголовки.
  - Сервисы внутри одного домена (например, PolicyManagement → Insurer) могут валидировать JWT самостоятельно (если требуется)
- **Связь Keycloak userId с business-сущностями**: при первом входе BFF выполняет поиск `policyholderId` по email/телефону в Policyholder Service и сохраняет соответствие `keycloakUserId` ↔ `policyholderId`. Это обеспечивает связь учётной записи с профилем клиента.
- **Сроки жизни токенов**: access token – 15 минут, refresh token – 1 день (конфигурируется в Keycloak).

## Рассматриваемые альтернативы

### Альтернатива 1: Auth0
- **Плюсы**: облачное решение с богатыми возможностями (2FA, социальные логины), минимальные затраты на поддержку.
- **Минусы**: дополнительная стоимость, данные пользователей передаются внешнему сервису (может не соответствовать политикам безопасности компании), нет прямой интеграции с корпоративным IAM.
- **Отклонена** из-за наличия готового Keycloak внутри компании и требований к хранению данных на собственной инфраструктуре.

### Альтернатива 2: Okta
- **Плюсы**: мощный корпоративный IAM, поддержка 2FA, интеграция с Active Directory.
- **Минусы**: высокая стоимость, сложность внедрения, не входит в существующий стек.
- **Отклонена** по аналогичным причинам (Keycloak уже развёрнут и покрывает базовые требования).

### Альтернатива 3: Самописный сервис аутентификации
- **Плюсы**: полный контроль над логикой, возможность кастомизации.
- **Минусы**: высокая стоимость разработки и поддержки, риск ошибок в безопасности, отсутствие встроенных механизмов 2FA и OIDC, дублирование функциональности, уже реализованной в Keycloak.
- **Отклонена** как неоправданно дорогая и рискованная альтернатива.

## Последствия
- **Плюсы**:
  - Использование уже развёрнутого Keycloak сокращает время внедрения и операционные затраты.
  - Единый источник идентификации для всех систем компании.
  - Встроенная поддержка 2FA через SMS без дополнительной разработки.
  - Возможность централизованного управления ролями и политиками безопасности.
- **Минусы**:
  - Требуется настройка Keycloak (создание клиента, настройка 2FA, шаблонов писем/SMS).
  - Управление ролевой моделью на уровне Keycloak непрозравно.
  - Зависимость от централизованной инфраструктуры (отказ Keycloak может повлиять на все системы).
- **Риски**:
  - Если Keycloak выйдет из строя, система не сможет аутентифицировать пользователей. Необходимо предусмотреть мониторинг и резервное копирование (обеспечивается централизованно).
  - Связывание `keycloakUserId` с `policyholderId` требует аккуратной реализации для предотвращения коллизий.
