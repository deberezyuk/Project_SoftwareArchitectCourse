# ADR-8: Формат передачи данных о поездке через Kafka (с учётом привязки метрик к геоданным)

## Контекст
В сценарии обработки телеметрии сервис `FormTripsTelemetry` (домен Telemetry) формирует поездку и публикует событие `trip_formed` в корпоративный Kafka. Потребителем является `FormTripWithMetrics` (домен DrivingAnalytics). Необходимо передать:
- Идентификаторы (tripId, sensorId, vehicleId)
- Временные метки (startTime, endTime)
- **Базовые метрики стиля вождения, привязанные к конкретным участкам маршрута** (например, координаты резких ускорений, торможений, превышений скорости)
- Агрегированные метрики (общее расстояние, средняя скорость, количество нарушений)
- Геоданные (маршрут поездки) – для отображения на карте с подсветкой нарушений

Геоданные могут содержать от нескольких десятков до нескольких тысяч точек. Объём данных может превышать стандартные лимиты сообщений Kafka (по умолчанию 1 МБ). Необходимо выбрать способ передачи, обеспечивающий:
- Производительность (минимальная задержка, пропускная способность)
- Надёжность (гарантии доставки, идемпотентность)
- Экономию сетевого трафика и места в Kafka
- Возможность отображения на карте нарушений в приложении
- Удобство обработки на стороне потребителя

## Решение с обоснованием
**Передаём в Kafka событие, содержащее метаданные поездки и агрегированные базовые метрики, а детальные геоданные с привязкой метрик к точкам сохраняем в объектном хранилище (MinIO/S3) и передаём ссылку на объект.**

### Ключевые элементы решения
1. **Формат сообщения в Kafka** – Avro (или Protobuf) для компактности и эволюции схемы. Сообщение содержит:
   - `tripId`, `sensorId`, `vehicleId`, `startTime`, `endTime`
   - `aggregatedMetrics` – объект с агрегированными данными (расстояние, средняя/макс скорость, количество нарушений по типам)
   - `geodataUrl` – ссылка на файл с детальными геоданными и привязанными к ним метриками

2. **Детальные геоданные**:
   - Формат: сжатый Parquet (или GeoJSON с gzip), хранящий массив записей, каждая из которых содержит:
     - `timestamp`, `lat`, `lon`, `speed`, `acceleration`, `braking`, `isHardBraking`, `isHardAcceleration`, `isSpeeding`, `isSharpTurn` и т.п.
   - Файл сохраняется в MinIO/S3 по пути `s3://bucket/trips/{tripId}/path.parquet` (или `.geojson.gz`).
   - Время жизни файлов соответствует времени хранения поездок в системе (например, 6 месяцев).

3. **Обработка потребителем**:
   - `FormTripWithMetrics` читает событие из Kafka, извлекает агрегированные метрики и ссылку на геоданные.
   - Для расчёта сложных метрик загружает файл из MinIO, если требуется детальный анализ.
   - Для отображения на карте в приложении (когда клиент запрашивает поездку) используется тот же файл – BFF загружает его и передаёт клиенту (или напрямую выдаёт подписанную ссылку).

### Обоснование выбора
- **Привязка метрик к геоданным**: детальный файл содержит все необходимые данные для отображения нарушений на карте (координаты и тип нарушения). Агрегированные метрики в Kafka позволяют быстро отображать список поездок без загрузки больших файлов.
- **Масштабируемость Kafka**: разгружаем брокеры от хранения больших бинарных данных.
- **Производительность**: уменьшение размера сообщений повышает пропускную способность Kafka.
- **Надёжность**: объектное хранилище обеспечивает durable storage с репликацией.
- **Гибкость**: можно легко добавлять новые поля в детальный файл без изменения схемы Kafka.
- **Стоимость**: объектное хранилище дешевле долгого хранения данных в Kafka.

## Рассматриваемые альтернативы

### Альтернатива 1: Передача всех данных в одном сообщении Kafka (с включением детальных геоданных и метрик)
- **Плюсы**: простота, нет дополнительного хранилища.
- **Минусы**: большие сообщения могут превышать лимиты, замедляют репликацию, дорогое хранение в Kafka. При длинных поездках возможны сбои.
- **Отклонена** как ненадёжная при масштабировании.

### Альтернатива 2: Передача только метрик в Kafka, а геоданные – отдельно (без привязки)
- **Плюсы**: минимальный размер сообщений.
- **Минусы**: потеря привязки нарушений к координатам; для отображения на карте потребуется отдельная синхронизация.
- **Отклонена** как неудовлетворяющая требованию привязки.

### Альтернатива 3: Передача списка нарушений с координатами в Kafka, а геоданные отдельно
- **Описание**: в Kafka передаётся массив событий нарушений с координатами, геоданные хранятся в MinIO. Агрегированные метрики не передаются.
- **Плюсы**: наружные данные доступны сразу, не нужно загружать весь трек.
- **Минусы**: для показа на карте всё равно нужны геоданные (линия маршрута), а без них карта будет неполной. Также увеличивается размер сообщения (список нарушений может быть большим). Агрегированные метрики всё равно нужно вычислять на стороне потребителя.
- **Отклонена** как менее удобная, чем хранение всех деталей в одном файле.

## Последствия
- **Разработка**:
  - Реализовать сохранение детального файла в MinIO (Parquet/GeoJSON) с генерацией уникального ключа.
  - Добавить в событие поле `geodataUrl`.
  - В `FormTripWithMetrics` добавить логику загрузки файла при необходимости.
- **Операционная нагрузка**:
  - Развернуть MinIO (или использовать корпоративное S3-хранилище) с высокой доступностью.
  - Настроить политики жизненного цикла для автоматического удаления старых файлов.
- **Безопасность**:
  - Ограничить доступ к MinIO только для сервисов внутри кластера.
  - Использовать временные подписанные URL для доступа из приложения (если требуется).
- **Масштабирование**:
  - MinIO легко масштабируется горизонтально, обеспечивая высокую пропускную способность.
- **Риски**:
  - Потеря ссылки на объект. Митигация: настроить согласованный TTL (объекты хранятся не менее времени жизни сообщений в Kafka).
  - Дополнительная задержка при обработке, если нужно загружать файл. Для ночного расчёта это некритично; для отображения на карте в реальном времени (клиент) – можно кэшировать результаты.

Решение принято с учётом необходимости детального отображения нарушений на карте и эффективного использования ресурсов Kafka.
