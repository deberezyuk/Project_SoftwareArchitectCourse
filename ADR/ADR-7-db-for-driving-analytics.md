# ADR-4: Подход для получения и предобработки данных из сервисов для фронтенда

## Контекст
Мобильное приложение требует агрегированных данных из разных доменов системы. Каждый экран приложения может запрашивать данные из 3–5 сервисов одновременно. Необходимо выбрать подход, который обеспечит:
- Минимальную задержку ответа.
- Простоту разработки и поддержки.
- Возможность адаптации под нужды конкретного клиента (мобильного приложения).
- Масштабируемость под растущую нагрузку.

## Решение с обоснованием

**Единый BFF (Backend for Frontend)** – напрямую вызывает микросервисы (без внутреннего API Gateway), использует параллельные запросы, кэширование (Redis) для редко меняющихся данных и возвращает агрегированный JSON.

**Обоснование:**
- **Производительность**: прямые вызовы между BFF и сервисами (внутри кластера) исключают лишние сетевые hop’ы; параллельные запросы сокращают время ответа.
- **Гибкость**: BFF может легко изменяться под нужды UI без влияния на другие сервисы (снижаем связность).
- **Безопасность**: BFF получает от External API Gateway уже проверенный JWT и заголовки с ролями (`X-User-Roles`, `X-Active-Role`), что позволяет ему не повторять аутентификацию.
- **Масштабируемость**: BFF горизонтально масштабируется независимо от других компонентов; использование Redis кэша снижает нагрузку на сервисы.
- **Простота**: нет необходимости в сложных инструментах (GraphQL) на начальном этапе, но архитектура позволяет в будущем добавить GraphQL-слой при необходимости.

**Детали реализации:**
- BFF реализован как отдельный микросервис.
- Принимает запросы от External API Gateway после валидации JWT. Gateway передаёт заголовки:
  - `Authorization: Bearer <JWT>`.
  - `X-User-Roles` – список ролей пользователя (из JWT).
  - `X-Active-Role` – роль, выбранная пользователем (передаётся клиентом после выбора).
- BFF для каждого запроса:
  1. Определяет набор сервисов для вызова на основе `X-Active-Role`.
  2. Выполняет **параллельные HTTP-запросы** к необходимым сервисам.
  3. Использует **Redis кэш** для данных, которые редко меняются (настройки уведомлений, настройки рекомендаций, справочные данные).
  4. Агрегирует ответы в единую структуру JSON, выполняет минимальную трансформацию (переименование полей, фильтрацию) и возвращает клиенту.
- **Обработка ошибок**:
  - Если критический сервис (Policyholder, Insurer) недоступен – возвращается HTTP 5xx.
  - Если некритичный сервис (Notification, Recommendation) недоступен – возвращается частичный ответ с полем `warnings`, содержащим информацию о недоступных данных.

## Рассматриваемые альтернативы

### Альтернатива 1: GraphQL
- **Плюсы**: клиент сам определяет структуру ответа, уменьшает количество запросов, упрощает эволюцию API.
- **Минусы**: требует внедрения Federation (схемы сервисов), более сложная настройка, команда не имеет опыт работы с GraphQL, избыточен для текущих потребностей.
- **Отклонена** на данном этапе, но может быть рассмотрена в будущем при усложнении клиентских потребностей.

### Альтернатива 2: Агрегация в API Gateway
- **Плюсы**: не требует отдельного BFF, централизация.
- **Минусы**: API Gateway становится тяжёлым, сложно кастомизировать под специфику мобильного приложения, ограниченные возможности для сложной трансформации данных, сложнее масштабировать отдельно.
- **Отклонена**, так как нарушает принцип разделения ответственности и усложняет поддержку.

### Альтернатива 3: Множественные запросы с клиента (каждый сервис напрямую)
- **Плюсы**: простота, нет дополнительного компонента.
- **Минусы**: клиент делает много запросов (до 5–6), увеличивается трафик, клиентская логика усложняется, сложно обеспечить консистентность, ухудшается производительностьх.
- **Отклонена** из-за неудовлетворительного пользовательского опыта и высокой связанности клиента с бэкендом.

## Последствия
- **Разработка**: требуется реализовать BFF с параллельными вызовами, кэшированием (Redis) и обработкой частичных ответов.
- **Операционная нагрузка**: добавление ещё одного сервиса (BFF) и Redis-кластера.
- **Масштабируемость**: BFF горизонтально масштабируется; при росте до 100 000 пользователей потребуется 5–10 реплик (зависит от нагрузки).
- **Безопасность**: BFF не должен повторно валидировать JWT, но должен доверять заголовкам от Gateway. При передаче JWT сервисам возможна дополнительная проверка.
- **Стоимость**: добавление Redis (можно использовать управляемый сервис или развернуть в кластере) увеличивает затраты, но снижает нагрузку на микросервисы.
- **Риски**:
  - BFF может стать узким местом при неправильном проектировании (слишком много зависимостей). Митигация: параллельные вызовы, оптимизация кода, горизонтальное масштабирование.
  - Дублирование логики трансформации между BFF и сервисами. Митигация: сервисы возвращают сырые бизнес-данные, BFF отвечает только за представление (DTO для UI).
  - Инвалидация кэша: необходимо подписаться на события изменения данных (Kafka) и удалять соответствующие записи из Redis. На начальном этапе можно использовать простое TTL, а затем добавить инвалидацию.

Это решение принято на основе требований к производительности, гибкости и простоте разработки.
