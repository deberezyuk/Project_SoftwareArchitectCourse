# ADR-5: Организация данных в домене DrivingAnalytics

## Контекст
В домене DrivingAnalytics работают микросервисы:
- **FormTripWithMetrics** – получает события `trip_formed` из Kafka, сохраняет данные о поездках, рассчитывает сложные метрики и записывает их в БД.
- **CalculateDrivingCoefficient** – запускается ночью, читает поездки с метриками за прошедшие сутки, рассчитывает обновлённый коэффициент стиля вождения, сохраняет его и историю в БД.
- **DrivingProfile** - позволяет читать и редактировать данные в профиле вождения.

Необходимо выбрать архитектуру хранения данных, которая обеспечит:
- Высокую производительность (запись интенсивная, чтение – аналитические запросы ночью).
- Отказоустойчивость.
- Масштабируемость при росте числа поездок.
- Минимальное дублирование данных и простоту разработки.

## Решение с обоснованием
**Используем единую PostgreSQL базу данных для сервисов с применением паттерна CQRS (разделение команд и запросов) через выделенную read replica.**

### Ключевые элементы решения
1. **Единая схема данных** – одна БД с таблицами поездок, метрик, профилей вождения. Это исключает сложную синхронизацию между разными хранилищами и упрощает эволюцию схемы.
2. **CQRS через репликацию** –  
   - **Command side (запись)**: сервис `FormTripWithMetrics` пишет в master-инстанс БД.  
   - **Query side (чтение)**: сервис `CalculateDrivingCoefficient` читает с read replica, что изолирует тяжёлые аналитические запросы от нагрузки записи.
3. **Отказоустойчивость** –  
   - Master-инстанс реплицируется асинхронно на одну или несколько реплик.  
   - При отказе master-а запись временно приостанавливается, чтение продолжается с реплики.  
   - Реплика может быть повышена до master-а (вручную или автоматически) для восстановления записи.
4. **Масштабируемость чтения** –  
   - Для аналитики можно добавить дополнительные read replica и балансировать нагрузку.  
   - При дальнейшем росте можно использовать специализированное аналитическое хранилище (например, ClickHouse) для выгрузки агрегированных данных.
5. **Минимизация дублирования** – единая схема устраняет необходимость дублировать данные между сервисами.

### Обоснование выбора
- **Производительность**: разделение нагрузки на запись и чтение предотвращает конфликты ресурсов. Ночные аналитические запросы не влияют на приём новых поездок.
- **Модифицируемость**: единая схема упрощает изменения (добавление полей, индексов) – требуется одна миграция.
- **Надёжность**: наличие read replica повышает доступность чтения; при сбое master-а можно переключить запись.
- **Масштабируемость**: легко добавлять реплики для увеличения пропускной способности чтения.
- **Стоимость**: использование managed PostgreSQL с read replica (например, AWS RDS) – стандартная практика с приемлемыми затратами.

## Рассматриваемые альтернативы

### Альтернатива 1: Две отдельные БД (одна для записи, другая для чтения, синхронизация через приложение)
- **Плюсы**: полная изоляция нагрузок, можно использовать разные типы СУБД.
- **Минусы**: сложная синхронизация (придётся дублировать данные через события или приложение), увеличение задержки, риск рассинхронизации, двойные затраты на инфраструктуру.
- **Отклонена** из-за высокой сложности и риска несогласованности.

### Альтернатива 2: Единая БД без реплики, но с оптимизацией запросов
- **Плюсы**: простота, минимальные затраты.
- **Минусы**: ночные аналитические запросы будут влиять на производительность записи; при росте объёма данных возможны блокировки и деградация.
- **Отклонена** как не обеспечивающая требуемую производительность и масштабируемость.

### Альтернатива 3: Использование отдельной БД для расчёта коэффициента с ETL из основной БД
- **Плюсы**: полная независимость.
- **Минусы**: сложность ETL-процессов, дублирование данных, задержка обновления.
- **Отклонена** как избыточная для текущих требований.

### Альтернатива 4: Две отдельные БД с синхронизацией через события (без CQRS)
- **Плюсы**: полная независимость сервисов (можно масштабировать БД по отдельности, использовать разные СУБД), отсутствие блокировок между записью и чтением, простота изоляции.

- **Минусы**: дублирование данных, увеличение объёма хранилища, сложность поддержания согласованности (возможна рассинхронизация), задержка передачи данных через Kafka (для ночного расчёта это некритично), дополнительная сложность обработки идемпотентности при дублировании сообщений.

- **Отклонена**: дублирование данных и дополнительная сложность синхронизации не оправданы, так как оба сервиса работают с одними и теми же сущностями в рамках одного домена. Использование единой БД с репликой даёт ту же изоляцию нагрузок без дублирования.

## Последствия
- **Разработка**: необходимо реализовать логику работы с read replica в сервисе `CalculateDrivingCoefficient`. Для этого можно использовать отдельный источник данных (datasource) в приложении.
- **Операционная нагрузка**: требуется настройка репликации PostgreSQL (управляемый сервис или самостоятельное администрирование). Необходимо мониторить лаг репликации, производительность master-а и реплик.
- **Безопасность**: read replica может быть доступна только для сервиса `CalculateDrivingCoefficient` через внутреннюю сеть.
- **Масштабирование**: при росте можно добавить дополнительные реплики для чтения или перейти на колоночное аналитическое хранилище.
- **Риски**:  
  - Задержка репликации может привести к тому, что `CalculateDrivingCoefficient` не увидит самые свежие поездки. Для ночного расчёта это некритично (лаг в несколько секунд допустим).  
  - Сбой master-а приведёт к остановке записи новых поездок до восстановления. Необходимо иметь процедуру переключения на реплику.

## Дополнительные решения для повышения отказоустойчивости и работы с нагрузкой на чтение
1. **Автоматическое переключение (failover)** – использовать managed сервис (например, AWS RDS Multi-AZ) или настроить Patroni для автоматического продвижения реплики при отказе master-а.
2. **Горизонтальное масштабирование чтения** – развернуть несколько read replica и балансировать запросы от `CalculateDrivingCoefficient` через внутренний балансировщик или с помощью клиентской логики (round-robin).
3. **Кэширование** – на уровне сервиса `CalculateDrivingCoefficient` кэшировать агрегированные результаты (например, в Redis) для снижения нагрузки на БД при повторных запросах. На начальном этапе кэш не используется, но архитектура готова к его внедрению.
4. **Партиционирование и индексация** – использовать TimescaleDB гипертаблицы для поездок (разбивка по времени), что улучшит производительность как записи, так и чтения.

Решение принято на основе баланса между простотой, производительностью и возможностью дальнейшего масштабирования.
