# ADR-7: Распределение нагрузки формирования рекомендаций

## Контекст
В системе умного автострахования реализуется функция формирования персонализированных рекомендаций для клиентов на основе их стиля вождения за прошедший месяц. Рекомендации генерируются во внешней LLM-платформе (асинхронно). Ключевые требования:
- Каждый клиент получает рекомендацию **ровно один раз в месяц** на основе данных за последний месяц.
- Количество клиентов – до 100 000, из них около 50 000 с включённой настройкой получения рекомендаций.
- Необходимо избежать пиковых нагрузок в конце месяца (когда все клиенты получают рекомендации).
- Обработка должна быть отказоустойчивой (при сбое – повтор), поддерживать горизонтальное масштабирование.
- В домене Recommendation работает один сервис (`RecommendationService`) со своей БД.

## Решение с обоснованием
**Используем комбинацию:**
1. **Планировщик на основе хэша ID клиента** для равномерного распределения запусков по дням месяца.
2. **Очередь заданий** (PostgreSQL с таблицей `pending_recommendations`) для отказоустойчивой обработки и масштабирования воркеров.

### Детали реализации
- Каждый день (например, в полночь) запускается планировщик (может быть отдельным компонентом или встроенным в `RecommendationService`). Он вычисляет, для каких клиентов наступил день генерации, используя формулу:  
  `(день_месяца) MOD (30) == (hash(clientId) % 30)`.  
  Для клиентов, подпадающих под условие, создаются записи в таблице `pending_recommendations` со статусом `pending` и временем создания.
- Воркеры (реплики `RecommendationService` в режиме консьюмера) периодически забирают из таблицы задания со статусом `pending` (например, с блокировкой строк `SELECT ... FOR UPDATE SKIP LOCKED`), обрабатывают их (собирают данные из DrivingAnalytics и MinIO, формируют запрос к LLM-платформе, сохраняют результат) и меняют статус на `done`. При ошибке (исключение, таймаут) задание возвращается в очередь (статус `pending` с увеличением счётчика попыток) или переводится в `failed` для последующего ручного вмешательства.
- После успешной генерации в БД Recommendations сохраняется сама рекомендация (текст, привязка к клиенту, дата) для отображения в приложении и хранения истории (не менее года).

**Обоснование выбора:**
- **Равномерное распределение**: хэш-функция от ID клиента обеспечивает статистически равномерное распределение клиентов по дням месяца, независимо от даты регистрации или других факторов. Это предотвращает накопление заданий в конце месяца.
- **Отказоустойчивость**: использование очереди на основе БД гарантирует, что задания не теряются при сбоях воркеров; механизм повторных попыток позволяет обработать их позднее.
- **Масштабируемость**: можно увеличивать количество реплик `RecommendationService`, работающих как воркеры, что позволяет параллельно обрабатывать несколько заданий. Планировщик остаётся единым.
- **Простота реализации**: не требует введения дополнительных компонентов (Redis, Kafka, внешних очередей). PostgreSQL уже используется в системе, таблица `pending_recommendations` легко создаётся и администрируется.

## Рассматриваемые альтернативы

### Альтернатива 1: Только планировщик с последовательной обработкой (без очереди)
- **Описание**: Планировщик каждый день запускает обработку для клиентов, подпадающих под формулу, и синхронно обрабатывает их в рамках одного потока.
- **Плюсы**: простота, минимум компонентов.
- **Минусы**:  
  - При сбое в день обработки клиент пропускает месяц (нет повторных попыток).  
  - Отсутствие параллелизма – обработка может не укладываться в одни сутки при росте числа клиентов.  
  - Масштабирование затруднено.
- **Отклонена** из-за низкой надёжности и ограниченной масштабируемости.

### Альтернатива 2: Только очередь заданий с внешним расписанием
- **Описание**: Внешний планировщик (например, Apache Airflow) добавляет задания для всех клиентов в начале месяца, а воркеры обрабатывают их в порядке очереди.
- **Плюсы**: централизованное управление расписанием, мощные механизмы мониторинга.
- **Минусы**:  
  - Риск неравномерной нагрузки: все задания могут накапливаться в начале месяца, создавая пик.  
  - Требуется введение дополнительной сложной инфраструктуры (Airflow), что избыточно.
- **Отклонена** из-за сложности и отсутствия встроенного равномерного распределения.

### Альтернатива 3: Только очередь с динамическим планированием на основе даты последнего успеха
- **Описание**: При завершении обработки клиента задание создаётся на следующий месяц (смещение на 30 дней). Воркеры обрабатывают задания в порядке FIFO.
- **Плюсы**: автоматическое выравнивание, не требует планировщика.
- **Минусы**:  
  - Со временем клиенты могут смещаться и накладываться, если обработка задерживается.  
  - Сложность восстановления после долгого простоя.  
  - Нет гарантии, что нагрузка будет равномерной (все могут накопиться к определённому дню).
- **Отклонена** из-за непредсказуемости распределения.

## Последствия
- **Разработка**:  
  - Создать таблицу `pending_recommendations` с полями: `id`, `client_id`, `status`, `created_at`, `retry_count`, `last_attempt`.  
  - Реализовать планировщик (можно встроить в `RecommendationService` как cron‑задачу).  
  - Реализовать воркеры, использующие `SELECT ... FOR UPDATE SKIP LOCKED` для безопасного захвата заданий.  
  - Обеспечить идемпотентность (проверка, не создана ли уже рекомендация за этот месяц).  
- **Инфраструктура**:  
  - Таблица будет в БД Recommendations (PostgreSQL). Необходимо добавить индексы по `status` и `created_at`.  
  - При необходимости можно настроить мониторинг длины очереди (количество `pending` записей).  
- **Масштабирование**:  
  - Увеличение количества реплик `RecommendationService` увеличивает параллелизм обработки.  
  - Планировщик может работать на одной реплике (с использованием блокировок или отдельного компонента).  
- **Надёжность**:  
  - Задания с ошибками автоматически повторяются (например, до 3 раз), после чего переводятся в статус `failed` для ручного разбора.  
  - Создание заданий на будущие дни не зависит от успешности предыдущих.  
- **Мониторинг**: добавить метрики: количество созданных заданий в день, среднее время обработки, количество повторных попыток, количество упавших.

Решение принято с учётом требований к надёжности, равномерной нагрузке и возможности плавного масштабирования без внесения избыточной сложности.
